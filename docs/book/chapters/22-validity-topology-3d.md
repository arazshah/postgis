## هندسه‌ی معتبر چیست

استاندارد OGC برای هر نوع هندسه قواعدی دارد. هندسه‌ای که این قواعد را رعایت نکند **نامعتبر** (invalid) است. PostGIS هندسه‌ی نامعتبر را
می‌پذیرد و ذخیره می‌کند، اما توابعی مثل `ST_Intersection`، `ST_Union` و `ST_Area` روی آن ممکن است خطا بدهند یا نتیجه‌ی **بی‌صدا و
غلط** برگردانند. پس اعتبار هندسه پیش‌شرط هر تحلیل است.

| قاعده | نقض آن | نام رایج |
|---|---|---|
| حلقه بسته باشد | نقطه‌ی آخر ≠ نقطه‌ی اول | حلقه‌ی باز |
| حلقه خودش را قطع نکند | دو ضلع حلقه از هم بگذرند | پاپیون (bowtie) |
| حلقه حداقل چهار نقطه داشته باشد | خط تبهگن | |
| حفره داخل حلقه‌ی بیرونی باشد | حفره بیرون زده | |
| حفره‌ها هم‌پوشانی نداشته باشند | دو حفره روی هم | |
| اجزای MultiPolygon هم‌پوشانی نداشته باشند | دو بخش روی هم | |
| حلقه در بیش از یک نقطه با خودش تماس نداشته باشد | گره‌ی خودتماس | |

```{.sql .run}
SELECT name, ST_IsValid(g) AS valid, ST_IsValidReason(g) AS reason
FROM (VALUES
  ('مربع سالم', 'POLYGON((0 0, 4 0, 4 4, 0 4, 0 0))'::geometry),
  ('پاپیون',    'POLYGON((0 0, 4 4, 4 0, 0 4, 0 0))'::geometry),
  ('حفره‌ی بیرون‌زده', 'POLYGON((0 0, 4 0, 4 4, 0 4, 0 0), (3 3, 6 3, 6 6, 3 6, 3 3))'::geometry),
  ('دو بخش هم‌پوشان', 'MULTIPOLYGON(((0 0, 4 0, 4 4, 0 4, 0 0)), ((2 2, 6 2, 6 6, 2 6, 2 2)))'::geometry)
) t(name, g);
```

`ST_IsValidReason` محل دقیق خطا را می‌گوید و `ST_IsValidDetail` همان را به صورت سطر (علت و نقطه‌ی هندسی محل خطا) برمی‌گرداند که می‌توان
روی نقشه نشانش داد.

::: know
**هندسه‌ی نامعتبر از کجا می‌آید؟** رقومی‌سازی دستی بی‌دقت، تبدیل از قالب CAD (DXF)، ساده‌سازی بدون حفظ توپولوژی (`ST_Simplify`)، گرد
کردن مختصات و تبدیل بین سیستم‌های مختصات. Shapefile و بسیاری از نرم‌افزارهای قدیمی اعتبار را بررسی نمی‌کنند؛ برای همین داده‌ی وارداتی
اغلب نامعتبر است.
:::

## اصلاح: ST_MakeValid

`ST_MakeValid` هندسه را بدون حذف هیچ رأسی معتبر می‌کند. نتیجه ممکن است **نوع دیگری** داشته باشد: پاپیون به MultiPolygon دوبخشی تبدیل می‌شود.

```{.sql .run}
SELECT ST_AsText(ST_MakeValid('POLYGON((0 0, 4 4, 4 0, 0 4, 0 0))'))                             AS bowtie_fixed,
       ST_Area(ST_MakeValid('POLYGON((0 0, 4 4, 4 0, 0 4, 0 0))'))                               AS fixed_area,
       ST_Area('POLYGON((0 0, 4 4, 4 0, 0 4, 0 0))'::geometry)                                   AS invalid_area,
       ST_AsText(ST_MakeValid('MULTIPOLYGON(((0 0,4 0,4 4,0 4,0 0)),((2 2,6 2,6 6,2 6,2 2)))',
                              'method=structure'))                                              AS overlap_fixed;
```

مساحت پاپیون نامعتبر **صفر** گزارش شد (دو مثلث با جهت مخالف هم را خنثی کردند) در حالی که مساحت واقعی ۸ است؛ نمونه‌ی کامل «نتیجه‌ی
بی‌صدا و غلط». از PostGIS ۳٫۲، `ST_MakeValid` دو روش دارد: `method=linework` (پیش‌فرض؛ همه‌ی خط‌ها را نگه می‌دارد) و `method=structure`
(حلقه‌ها را بر اساس ساختار بیرونی/حفره بازسازی می‌کند و برای اجزای هم‌پوشان، اجتماعشان را می‌گیرد).

دستور اصلاح یک لایه، با حفظ نوع ستون:

```sql
UPDATE parks
SET geom = ST_Multi(ST_CollectionExtract(ST_MakeValid(geom), 3))
WHERE NOT ST_IsValid(geom);
```

`ST_CollectionExtract(…, 3)` فقط بخش‌های چندضلعی را نگه می‌دارد (اگر اصلاح، خط یا نقطه‌ی اضافه ساخته باشد) و `ST_Multi` همه را چندبخشی
می‌کند تا با نوع ستون `MultiPolygon` جور شود. دکمه‌ی «اصلاح هندسه» در «سلامت داده» (فصل ۷) همین کار را می‌کند.

::: warn
**پس از اصلاح، بسنجید.** `ST_MakeValid` معتبر می‌کند، اما «درست» نمی‌کند. پاپیونی که از خطای رقومی‌سازی آمده، با اصلاح خودکار به دو مثلث
تبدیل می‌شود، در حالی که منظور رقومی‌کننده احتمالاً یک چهارضلعی بوده است. پس از اصلاح انبوه، تعداد عارضه‌هایی را که نوع یا مساحتشان
محسوس عوض شده بشمارید و آن‌ها را دستی بازبینی کنید. ترفند قدیمی `ST_Buffer(geom, 0)` هم گاهی معتبر می‌کند، اما ممکن است بخشی از هندسه
را بی‌صدا حذف کند؛ `ST_MakeValid` امن‌تر است.
:::

## قواعد توپولوژی با SQL

اعتبار هر عارضه به تنهایی کافی نیست؛ **رابطه‌ی** عارضه‌ها هم قاعده دارد. لایه‌ی قطعه‌های ثبتی نباید همپوشانی یا شکاف داشته باشد؛ خط‌های
شبکه‌ی آب باید در گره‌ها به هم برسند. این قواعد را می‌توان با SQL بررسی کرد:

**همپوشانی** (فصل ۱۷):

```{.sql .run}
SELECT count(*) AS overlapping_parcel_pairs
FROM parcels a JOIN parcels b ON a.id < b.id AND ST_Overlaps(a.geom, b.geom);
```

**شکاف** بین چندضلعی‌هایی که باید پیوسته باشند: حفره‌های اجتماع آن‌ها. اگر اجتماع لایه حفره داشته باشد، یا شکاف واقعی است (مثلاً معبر) یا
خطای رقومی‌سازی:

```sql
SELECT ST_MakePolygon(ST_InteriorRingN(u, n)) AS gap, ST_Area(ST_MakePolygon(ST_InteriorRingN(u, n))::geography) AS m2
FROM (SELECT (ST_Dump(ST_Union(geom))).geom AS u FROM parcels_cadastre) x,
     generate_series(1, ST_NumInteriorRings(u)) n
ORDER BY m2;   -- شکاف‌های بسیار کوچک (sliver) معمولاً خطا هستند
```

**گره‌ی آویزان** در شبکه‌ی خطی: انتهای خطی که به هیچ خط دیگری نرسیده است. در شبکه‌ی معابر، آویزان‌ها مسیریابی را خراب می‌کنند (فصل ۲۴):

```sql
WITH ends AS (
  SELECT gid, ST_StartPoint(geom) AS p FROM roads UNION ALL
  SELECT gid, ST_EndPoint(geom) FROM roads
)
SELECT e.gid, e.p
FROM ends e
WHERE NOT EXISTS (SELECT 1 FROM roads r WHERE r.gid <> e.gid AND ST_DWithin(r.geom, e.p, 0.000001));
```

برای بستن شکاف‌های باریک بین دو لایه یا دو عارضه، `ST_Snap(a, b, tolerance)` رأس‌های a را به b می‌چسباند (فصل ۱۸).

## توپولوژی ذخیره‌شده: postgis_topology

مدل «ویژگی‌های ساده» هر چندضلعی را مستقل نگه می‌دارد: مرز مشترک دو قطعه **دو بار** ذخیره می‌شود. افزونه‌ی `postgis_topology` مدل دیگری
دارد: داده را به **گره** (node)، **یال** (edge) و **وجه** (face) می‌شکند و هر مرز مشترک فقط **یک بار** ذخیره می‌شود. اگر آن مرز را ویرایش
کنید، هر دو قطعه با هم عوض می‌شوند؛ شکاف و همپوشانی از اساس ممکن نیست. این مدل برای کاداستر، تقسیمات کشوری و شبکه‌ها مناسب است.

```{.sql .run}
SELECT topology.CreateTopology('parcels_topo', 4326, 0.0000001);
SELECT topology.AddTopoGeometryColumn('parcels_topo', 'public', 'parcels', 'topo', 'POLYGON');
UPDATE parcels SET topo = topology.toTopoGeom(geom, 'parcels_topo', 1, 0.0000001);

SELECT (SELECT count(*) FROM parcels_topo.node) AS nodes,
       (SELECT count(*) FROM parcels_topo.edge) AS edges,
       (SELECT count(*) FROM parcels_topo.face) AS faces;
```

۱۲ قطعه‌ی نمونه به ۱۲ یال و ۱۳ وجه تبدیل شدند (وجه شماره‌ی صفر، «جهان بیرونی» است). چون قطعه‌های نمونه از هم جدا هستند، هیچ یالی بین دو قطعه
مشترک نیست؛ در لایه‌ی کاداستر واقعی، تعداد یال‌ها بسیار کمتر از مجموع اضلاع قطعه‌هاست و همین «صرفه‌جویی» ضامن سازگاری است. ستون `topo`
هندسه‌ی هر قطعه را از روی یال‌ها می‌سازد (`topo::geometry`) و توابعی مثل `topology.ST_ChangeEdgeGeom` یک یال مشترک را برای همه‌ی قطعه‌های
مجاور ویرایش می‌کنند.

::: pro
**تلورانس توپولوژی.** آخرین عدد در `CreateTopology` و `toTopoGeom` تلورانس است: رأس‌هایی نزدیک‌تر از این فاصله یکی شمرده می‌شوند. در SRID
۴۳۲۶، `0.0000001` درجه حدود یک سانتی‌متر است. تلورانس بزرگ رأس‌های واقعی را ادغام می‌کند و تلورانس خیلی کوچک شکاف‌های میکروسکوپی را باقی
می‌گذارد. برای داده‌ی کاداستر در UTM، تلورانس را به متر (مثلاً ۰٫۰۱) بگذارید.
:::

## هندسه‌ی سه‌بعدی

### مختصات Z

هر رأس می‌تواند ارتفاع (Z) داشته باشد (فصل ۲). توابع دوبعدی Z را **نادیده می‌گیرند**؛ برای محاسبات سه‌بعدی توابع `3D` هست:

```{.sql .run}
WITH p AS (SELECT 'POINT Z (0 0 0)'::geometry AS a, 'POINT Z (30 40 120)'::geometry AS b,
                  'LINESTRING Z (0 0 1200, 300 400 1350, 600 800 1290)'::geometry AS road)
SELECT ST_Distance(a, b)    AS distance_2d,
       ST_3DDistance(a, b)  AS distance_3d,
       ST_Length(road)      AS road_2d,
       round(ST_3DLength(road)::numeric, 1) AS road_3d,
       ST_ZMax(road) - ST_ZMin(road)        AS elevation_range
FROM p;
```

طول سه‌بعدی جاده‌ی کوهستانی (طول واقعی که خودرو می‌پیماید) از طول افقی بیشتر است. `ST_Force2D` و `ST_Force3D` بُعد را حذف یا اضافه
می‌کنند. برای افزودن ارتفاع از DEM به نقطه‌ها، فصل ۲۳ را ببینید.

### SFCGAL: عملیات سه‌بعدی واقعی

افزونه‌ی `postgis_sfcgal` عملیات هندسی سه‌بعدی را اضافه می‌کند. پرکاربردترینشان **اکسترود** است: ساختن حجم سه‌بعدی ساختمان از ردپای
دوبعدی و ارتفاع آن:

```{.sql .run}
WITH b AS (SELECT ST_Extrude('POLYGON((0 0, 20 0, 20 12, 0 12, 0 0))'::geometry, 0, 0, 15) AS g)
SELECT ST_GeometryType(g)                                         AS building_3d,
       ST_NumGeometries(g)                                        AS faces,
       round(ST_Volume(ST_MakeSolid(g))::numeric)                 AS volume_m3,
       (SELECT round(sum(ST_3DArea((d).geom))::numeric) FROM ST_Dump(g) d) AS surface_m2
FROM b;
```

سطح بیرونی را با جمع مساحت سه‌بعدی تک‌تک وجه‌ها (`ST_Dump`) حساب کرده‌ایم؛ در بعضی نسخه‌ها `ST_3DArea` روی کل سطح چندوجهی صفر برمی‌گرداند
و این روش مطمئن‌تر است.

ساختمانی ۲۰ در ۱۲ متر با ارتفاع ۱۵ متر: ۳۶۰۰ متر مکعب حجم و ۱۴۴۰ متر مربع سطح بیرونی (برای برآورد نما یا عایق‌کاری). `ST_3DIntersection`،
`ST_3DUnion` و `ST_StraightSkeleton` (اسکلت سقف) هم در این افزونه‌اند. نمایش سه‌بعدی نتیجه در QGIS (نمای سه‌بعدی) یا کتابخانه‌های وب سه‌بعدی
انجام می‌شود.

::: real
**ساختمان‌های OSM در سه‌بعد.** داده‌ی آماده‌ی ایران (فصل ۳۰) ردپای ساختمان‌ها را از OpenStreetMap می‌آورد و برای بعضی، تعداد طبقه
(`building:levels`). با فرض سه متر برای هر طبقه، `ST_Extrude(geom, 0, 0, levels * 3)` مدل سه‌بعدی ساده‌ی شهر را می‌سازد؛ پایه‌ی تحلیل
سایه، دید و تراکم ساختمانی.
:::

::: summary
- هندسه‌ی نامعتبر (پاپیون، حفره‌ی بیرون‌زده، اجزای هم‌پوشان) نتیجه‌ی بی‌صدا و غلط می‌دهد؛ `ST_IsValid` و `ST_IsValidReason` آن را می‌یابند.
- `ST_MakeValid` (با روش linework یا structure) معتبر می‌کند؛ با `ST_CollectionExtract` و `ST_Multi` نوع را حفظ و نتیجه را بازبینی کنید.
- قواعد توپولوژی (همپوشانی، شکاف، آویزان) با SQL قابل بررسی‌اند.
- `postgis_topology` مرزهای مشترک را یک بار ذخیره می‌کند (گره، یال، وجه) و سازگاری را تضمین می‌کند.
- توابع `3D` ارتفاع را در فاصله و طول حساب می‌کنند؛ SFCGAL اکسترود، حجم و سطح سه‌بعدی می‌دهد.
:::

::: teach
**زمان پیشنهادی:** یک و نیم جلسه. یک Shapefile واقعی و قدیمی با هندسه‌ی نامعتبر به کلاس بیاورید و ابتدا با آن `ST_Union` بگیرید تا
خطا ببینند؛ سپس بشمارند، علت را پیدا و اصلاح کنند. «مساحت صفر پاپیون» را حتماً نشان دهید.
:::
