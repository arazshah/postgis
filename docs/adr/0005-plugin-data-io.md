# ADR-0005: ورود و خروج داده با handler سطح ۲ (پیشنهادی)

وضعیت: **پذیرفته و پیاده‌سازی‌شده** (چهار تصمیم انتهای سند تأیید شد). تفاوت با پیش‌نویس: ورود و خروجی در مانیفست جدا اعلام نمی‌شوند؛ خود صفحه‌ی کیت `[[imports]]` و `[[exports]]` را اعلام می‌کند (مثل `[[forms]]`) و handler باید در `handlers` بسته باشد. مرجع: ADR-0002 (سطح ۲)، ADR-0004، `docs/plugins/tier2.md`.

## مسئله
یک پلاگین باید بتواند **قالب فایلی را که سامانه نمی‌شناسد وارد** کند (مثلاً خروجی یک دستگاه GPS، فایل متنی یک سازمان) یا **خروجی با قالب اختصاصی** بسازد (مثلاً گزارش مخصوص یک مشتری). این‌ها منطق پایتونی می‌خواهند، پس سطح ۲. تفاوتش با handlerهای فعلی: **اولین بار است کد پلاگین با فایل مشتری سروکار پیدا می‌کند** و داده‌ای باید در پایگاه او نوشته شود.

## اصل
**کد پلاگین فقط تبدیل می‌کند؛ هسته می‌نویسد.** handler هیچ‌وقت به پایگاه داده‌ی مشتری برای نوشتن، به فایل‌سیستم یا شبکه دست نمی‌زند. بایت فایل را می‌گیرد و جدول/متن برمی‌گرداند؛ نوشتن در پایگاه یا ساختن پاسخ دانلود را کد معتبر و آزموده‌ی هسته انجام می‌دهد (مثل `[[forms]]` که SQL را هسته می‌سازد).

## قرارداد

### ورود (importer)
```toml
# در صفحه‌ی کیت (need = "editor" یا بالاتر)
[[imports]]
key = "gps"
title = "ورود فایل دستگاه GPS"
handler = "parse_gps"          # باید در handlers بسته باشد
extensions = [".trk", ".gps"]  # فیلتر انتخاب فایل و بررسی پسوند؛ اعتبار واقعی با handler است
```
```python
def handle(ctx, params):
    data = ctx.file()          # bytes، حداکثر ۳ مگابایت
    ...
    return {"columns": [{"name": "at", "type": "timestamptz"}, {"name": "lat", "type": "double"},
                        {"name": "lon", "type": "double"}, {"name": "note", "type": "text"}],
            "rows": [["2026-01-01T10:00:00Z", 35.7, 51.4, "x"], ...],
            "geometry": {"lat": "lat", "lon": "lon"}}   # اختیاری: ستون نقطه‌ی WGS84 را هسته می‌سازد
```
- **هسته می‌سازد:** `CREATE TABLE` با نام و ستون‌های اعتبارسنجی‌شده و `INSERT` با پارامتر متصل (نه متن handler). نوع ستون فقط از فهرست سفید: `text`، `integer`، `bigint`، `double`، `boolean`، `date`، `timestamptz`، `jsonb`.
- **v1 فقط «ساخت جدول تازه» است.** `overwrite` و `append` عمداً نیست: نمی‌خواهیم کد خارجی داده‌ی موجود را عوض کند.
- نام جدول را کاربر می‌دهد و همان قواعد نام‌گذاری فعلی سامانه اعمال می‌شود؛ جدول از قبل موجود = خطا.
- سقف: ۲۰٬۰۰۰ ردیف، ۵۰ ستون، نتیجه‌ی JSON حداکثر ۴ مگابایت، ۱۲۰ نویسه برای نام ستون.
- هندسه: `geometry = {lat, lon}` ستون `geometry(Point, 4326)` می‌سازد و هسته با `ST_MakePoint` پر می‌کند؛ WKT/GeoJSON دلخواه از handler **نمی‌گیریم** (v1).

### خروجی (exporter)
```toml
[[exports]]
key = "rep"
title = "گزارش اختصاصی"
handler = "to_report"
format = "csv"                 # csv | json | txt | geojson ← تعیین‌کننده‌ی Content-Type
```
```python
def handle(ctx, params):
    rows = ctx.sql("select ...")["rows"]       # فقط‌خواندنی با نقش محدود مشتری، همان سقف‌های سطح ۲
    return {"filename": "report", "text": "a,b\n1,2\n"}
```
- پاسخ: `Content-Disposition: attachment`، `X-Content-Type-Options: nosniff` و **نوع از فهرست سفید قالب** (هرگز HTML)؛ نام فایل پاک‌سازی می‌شود (بدون مسیر و نویسه‌ی کنترلی).
- سقف خروجی: ۴ مگابایت.

## امنیت

| تهدید | مهار |
|---|---|
| کد مخرب داده بنویسد یا بخواند | handler اتصال نوشتن ندارد؛ نوشتن فقط با `INSERT` پارامتری هسته و فقط جدول تازه؛ خواندن فقط با `ctx.sql` فقط‌خواندنی |
| فایل مخرب (zip bomb، فایل بسیار بزرگ) | سقف ۳ مگابایت پیش از رسیدن به handler، مهلت و سقف حافظه‌ی جعبه (همان rlimit)؛ handler فایل را فقط در حافظه می‌بیند |
| خروجی HTML/اسکریپت (XSS) | فقط `attachment` با Content-Type فهرست سفید و `nosniff` |
| تزریق SQL از راه نام ستون/جدول | هسته نام‌ها را با الگوی سخت‌گیر و `Identifier` می‌سازد؛ مقدارها همه پارامتر |
| پر کردن دیسک/سهمیه‌ی مشتری | سقف ردیف و حجم؛ سقف سهمیه‌ی پلن همچنان اعمال می‌شود (خطای پایگاه داده به پیام کوتاه تبدیل می‌شود) |
| نشت داده بین مشتریان | اجرای هر handler فقط با داده‌ی همان پایگاه؛ توکن کار یک‌پایگاهی (همان سطح ۲)؛ فایل پس از اجرا نگه داشته نمی‌شود |
| سوءاستفاده‌ی مکرر | سطح دسترسی (ورود: editor، خروج: viewer)، مجوز پلاگین، معیار `io_runs` با سقف ماهانه‌ی مجوز، ثبت در گزارش فعالیت، و قطع‌کن خودکار |

## یکپارچگی با رابط
- **v1: داخل صفحه‌ی خود پلاگین** (کیت صفحه): بلوک «ورود فایل» و دکمه‌ی «خروجی» با اجزای سیستم طراحی. پلاگین سیستمی `databases` و مودال ورود فعلی **دست نمی‌خورند**.
- v2 (در صورت نیاز): ثبت importer در مودال ورود اصلی از راه یک نقطه‌ی توسعه‌ی هسته؛ نیازمند تغییر در `databases` و جدا برنامه‌ریزی می‌شود.

## تصمیم‌هایی که تأیید می‌خواهند
۱. v1 فقط «جدول تازه» (بدون append/overwrite) — پیشنهاد: بله.
۲. سقف ورودی ۳ مگابایت و ۲۰٬۰۰۰ ردیف — پیشنهاد: بله؛ قالب‌های بزرگ‌تر بعداً با انتقال فایل از راه فایل موقت.
۳. جای رابط: صفحه‌ی پلاگین (v1) نه مودال ورود اصلی — پیشنهاد: بله.
۴. هندسه فقط نقطه از `lat/lon` — پیشنهاد: بله؛ WKT/GeoJSON دلخواه بعداً با اعتبارسنجی PostGIS.

## هنوز نیست (خارج از این ADR)
استریم فایل بزرگ، ورود رستر، append/overwrite، importer در مودال اصلی، ورود زمان‌بندی‌شده.
