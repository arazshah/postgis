# ADR-0001: سامانه‌ی پلاگین برای ابزارهای تحلیل (و بعد بقیه‌ی بخش‌ها)

**وضعیت:** پیشنهادی (منتظر تأیید؛ هنوز کدی تغییر نکرده)
**تاریخ:** ۱۴۰۵/۰۸/۲۰ (2026-11-11)
**تصمیم‌گیرنده:** مالک محصول + تیم توسعه

---

## ۱. خلاصه برای تصمیم

بخش «ابزارها» امروز کار می‌کند و ۱۶ ابزار دارد، ولی **پلاگین‌پذیر نیست**: هر ابزار تازه یعنی دست بردن در دست‌کم ۷ فایل مشترک
(آخرین بار افزودن ۹ ابزار ۱۴ فایل را عوض کرد). پیشنهاد این است:

1. یک **SDK کوچک ابزار** (`tools/sdk`) با کلاس پایه، انواع پارامتر و «زمینه‌ی اجرا» ساخته شود؛ هر ابزار یک ماژول مستقل شود.
2. یک **رجیستری** ابزارها را خودکار کشف کند (از هر اپ جنگو یا بسته‌ی pip) و هنگام راه‌اندازی اعتبارسنجی کند.
3. در **پنل مدیریت** بخش «افزونه‌ها و ابزارها» بیاید: روشن/خاموش، ترتیب، دسترسی بر اساس پلن، بتا، آمار اجرا و خطا، آزمون سلامت.
4. همین الگو (نقطه‌ی توسعه + رجیستری + کنترل در ادمین) بعداً به بقیه‌ی بخش‌ها (کارهای پس‌زمینه، ریل پایگاه، ناوبری ادمین، اعلان‌ها، داشبورد) تعمیم داده شود تا **هر بخش توسعه یک پلاگین** باشد.

اجرا در ۴ فاز، فاز صفر **بدون هیچ تغییر رفتاری** (همان SQL، همان صفحه، همان آدرس‌ها) و با آزمون «SQL طلایی» تضمین می‌شود.

**کد پایتون پلاگین از پنل ادمین بارگذاری نمی‌شود** (یعنی اجرای کد دلخواه روی سرور)؛ پلاگین با PR و بازبینی وارد می‌شود و ادمین فقط فعال‌سازی و تنظیم می‌کند.

### نقاط قوت که حفظ می‌شوند
- فرم از روی داده‌ی پارامتر ساخته می‌شود (بدون if در قالب).
- SQL فقط با `psycopg.sql` (Identifier/Literal) ساخته می‌شود؛ تزریق SQL نداریم.
- اجرا با `SET ROLE` نقش خود مشتری و `statement_timeout`؛ پلاگین در سطح پایگاه داده نمی‌تواند از حق کاربر بالاتر برود.
- خط لوله‌ی مشترک خروجی (`_fix_geom_type`، کلید `gid`، نمایه‌ی GiST، `ANALYZE`، واگذاری مالکیت) — همه‌ی ابزارها خروجی سالم و یکسان دارند.
- اجرا در صف پس‌زمینه با پیشرفت و اعلان.

## ۳. نیازمندی‌ها

**کارکردی**
- افزودن ابزار = افزودن **یک پوشه** (یا یک بسته‌ی pip)، بدون تغییر فایل مشترک.
- فرم، کارت گالری، تاریخچه، اعلان، خلاصه، پیشنهاد نمودار و راهنما از خود پلاگین بیاید.
- ادمین بدون deploy: روشن/خاموش، بتا (فقط کارکنان یا کاربران انتخابی)، ترتیب و «ویژه»، پلن‌های مجاز، بازنویسی عنوان/توضیح، سقف زمان.
- ادمین ببیند: پلاگین‌های بارگذاری‌شده، نسخه، نویسنده، خطای بارگذاری، تعداد اجرا، درصد شکست، میانگین زمان.

**غیرکارکردی**
- بدون تغییر رفتار برای کاربر در فاز صفر.
- امنیت: SQL فقط `Composable`؛ اجرا با نقش مشتری؛ پلاگین به اتصال مدیر دسترسی مستقیم نداشته باشد.
- قابل آزمون بدون PostgreSQL (ساخت SQL) و با PostgreSQL (اجرای واقعی).
- سازگار با سیستم طراحی (آیکون از `core/icons.py`، چیپ به‌جای select کوتاه، ۴۰۰ پیکسل).

## ۴. گزینه‌ها

### گزینه‌ی الف: نگه داشتن ساختار فعلی و فقط مستندسازی «چک‌لیست افزودن ابزار»
| بعد | ارزیابی |
|---|---|
| پیچیدگی | کم |
| هزینه | تقریباً صفر |
| مقیاس‌پذیری | بد؛ از ~۳۰ ابزار به بعد فایل موتور غیرقابل نگهداری |
| کار تیمی | تعارض دائمی روی `analysis/tools.py` |

**مزیت:** کاری لازم نیست. **عیب:** هیچ‌کدام از خواسته‌ها (ماژولار، ادمین) برآورده نمی‌شود.

### گزینه‌ی ب (پیشنهادی): SDK درون‌برنامه‌ای + رجیستری + کشف خودکار + کنترل ادمین
| بعد | ارزیابی |
|---|---|
| پیچیدگی | متوسط (یک بازسازی یک‌باره، بعد ساده‌تر از امروز) |
| هزینه | فاز صفر و یک: حدود ۱–۱٫۵ هفته کار یک نفر |
| مقیاس‌پذیری | خوب؛ صدها ابزار، چند تیم موازی |
| آشنایی تیم | بالا؛ همان جنگو و psycopg، الگوی `AppConfig.ready` و `autodiscover_modules` (مثل `admin.py`) |

**مزیت:** هر ابزار مستقل، آزمون‌پذیر، قابل خاموش کردن؛ امکان بسته‌ی pip جدا برای تیم/مشتری. **عیب:** یک بازسازی اولیه؛ نیاز به نسخه‌گذاری API.

### گزینه‌ی ج: پلاگین اعلانی (SQL الگو) که در پنل ادمین نوشته شود
| بعد | ارزیابی |
|---|---|
| پیچیدگی | بالا (موتور الگو، اعتبارسنجی، sandbox) |
| امنیت | پرخطر؛ ادمین با یک الگوی بد می‌تواند داده‌ی مشتری را خراب کند؛ آزمون و بازبینی کد دور زده می‌شود |
| انعطاف | کم؛ ابزارهایی مثل `netnearest` و `voronoi` منطق پایتونی (سقف، شرط نوع هندسه) دارند |

**مزیت:** ابزار ساده بدون deploy. **عیب:** چرخه‌ی کیفیت (PR، آزمون، `ruff`) را دور می‌زند.

### گزینه‌ی د: سرویس جدا برای هر ابزار (میکروسرویس/وب‌هوک)
پیچیدگی و هزینه‌ی عملیاتی بالا، اتصال به پایگاه مشتری از بیرون، برای اندازه‌ی فعلی تیم زیاده‌روی است.

### تحلیل
خواسته‌ی اصلی «توسعه‌ی مستمر و ماژولار توسط تیم» است و ابزار کد حساس (SQL روی داده‌ی مشتری) اجرا می‌کند؛ پس جای پلاگین **مخزن کد و چرخه‌ی PR** است و جای **کنترل** پنل ادمین. گزینه‌ی ب هر دو را می‌دهد.
گزینه‌ی ج را می‌شود بعداً، محدود و اختیاری، روی همین SDK به‌عنوان «یک نوع پلاگین» ساخت (فاز ۳) — اگر واقعاً لازم شد.

**تصمیم پیشنهادی: گزینه‌ی ب.**

## ۵. طراحی پیشنهادی

### ۵.۱ ساختار پوشه


کشف: در `ToolsConfig.ready()` → `autodiscover_modules("geotools")` (هر اپ نصب‌شده) + ماژول‌های `tools/plugins/*/plugin.py` + entry point پایتون `geopaygah.tools` برای بسته‌های pip جدا.

### ۵.۲ قرارداد پلاگین (نمونه‌ی بافر)

```python
from psycopg import sql
from tools.sdk import ToolPlugin, register, params as P


@register
class Buffer(ToolPlugin):
    key = "buffer"                      # یکتا؛ برای اپ‌های دیگر: "satellite.ndvi"
    version = "1.0"
    api_version = 1
    title = "حریم (بافر)"
    description = "دور هر عارضه حریمی به فاصله دلخواه می‌کشد."
    category = "proximity"
    icon = "t-buffer"                   # باید در core/icons.py و studio-ui.js باشد
    inputs = ("هر لایه",)
    output = "چندضلعی حریم"
    example = "حریم ۵۰۰ متری ایستگاه‌های مترو را بساز…"
    columns = ("ستون‌های لایه ورودی", "geom")
    requires = ()                       # مثلاً ("routing",) یا ("ext:pgrouting", "plan:raster")
    chart_hint = None                   # {"kind": "hist", "field": "distance_m"}
    params = (
        P.Layer("layer", "لایه ورودی"),
        P.Number("distance", "فاصله (متر)", default=500, min=1, max=100_000, help="فاصلهٔ حریم از هر عارضه"),
        P.Bool("dissolve", "همه حریم‌ها یکی شوند", required=False),
    )

    def build(self, ctx, v):            # v = مقادیر اعتبارسنجی‌شده و تبدیل‌شده
        t = v.layer                     # TableRef
        col, srid, _ = ctx.geom_of(t)
        g = ctx.geom4326("s", col, srid)
        if v.dissolve:
            return sql.SQL("SELECT ST_Multi(ST_Union(ST_Buffer({g}::geography, {d})::geometry))"
                           "::geometry(MultiPolygon, 4326) AS geom FROM {src} s").format(
                g=g, d=sql.Literal(v.distance), src=ctx.ident(t))
        ...

    def summary(self, v):               # اختیاری؛ پیش‌فرض از روی params ساخته می‌شود
        return f"{v.layer.name} · فاصله {v.distance:g} متر"

    def after_create(self, ctx, conn, target):   # اختیاری؛ مثل بررسی «مسیر خالی» در route
        pass
```

نکته‌ها:
- **یک منبع حقیقت:** عنوان، آیکون، فرم، منطق، خلاصه و نمودار همه در یک کلاس؛ `TOOLS`، `_INFO`، `PUBLIC_PARAMS`، `ICONS`، `CHART_HINTS`، `NEW_TOOLS` حذف می‌شوند.
- **پارامترها خودشان اعتبارسنجی می‌کنند** (بازه، ارقام فارسی، نوع هندسه)؛ فرم `min/max` و `inputmode` را از همان می‌گیرد.
- **انواع پارامتر تازه:** `Column(of="other", types=NUMERIC)` (انتخاب ستون از لایه‌ی انتخاب‌شده؛ مشکل ۷)، `Point` (کلیک روی نقشه به‌جای تایپ طول/عرض)، `Choice` (چیپ)، `Layer(geom=...)`، `Bool`، `Number`، `Text`. نوع تازه با `params.register_kind()` و یک قطعه‌ی قالب `templates/tools/params/<kind>.html` اضافه می‌شود.
- **خروجی `build` باید `sql.Composable` باشد**؛ رانر در غیر این صورت خطا می‌دهد (پشتیبان امنیتی در برابر f-string).
- **پلاگین اتصال خام نمی‌گیرد**؛ `ctx` فقط خواندن کاتالوگ را می‌دهد و `after_create` اتصالی می‌گیرد که پیش از آن `SET ROLE` شده است. (قوی‌تر: اجرای مرحله‌ی کاربر با اتصال جداگانه‌ی نقش مشتری به‌جای `SET ROLE`، تا `RESET ROLE` هم بی‌اثر باشد — در فاز ۱ بررسی شود.)
- **نوع خروجی** در آینده: `output_kind = "table" | "view" | "report"` (گزارش متنی بدون جدول، نمای زنده مثل «یافتن عارضه»).
- **نسخه:** `ToolRun` نسخه‌ی پلاگین را نگه می‌دارد و `upgrade_params(old_version, params)` اختیاری «اجرای دوباره» را سالم نگه می‌دارد.

### ۵.۳ رجیستری و اعتبارسنجی هنگام راه‌اندازی (`tools/checks.py`)
برای هر پلاگین: کلید یکتا و قالب `[a-z][a-z0-9_.]{1,63}`، `api_version` پشتیبانی‌شده، آیکون موجود در `core/icons.py` و `static/js/studio-ui.js`، دسته‌ی ثبت‌شده، نام پارامترها یکتا و بدون برخورد با `output`/`replace`، `requires` شناخته‌شده، عنوان و مثال فارسی غیرخالی.
پلاگینی که بارگذاری‌اش خطا بدهد **کل سایت را نمی‌خواباند**: ثبت نمی‌شود، خطایش در ادمین نمایش داده می‌شود و `manage.py check` در CI شکست می‌خورد.

### ۵.۴ پیش‌نیازها (جایگزین `_blocked`)
`requires` به «بررسی‌کننده‌»های ثبت‌شده نگاشت می‌شود که هرکدام متن فارسی دلیل و لینک رفع برمی‌گرداند:
`routing` (جدول `routing.ways`)، `ext:<name>` (افزونه‌ی نصب‌شده روی پایگاه)، `plan:<feature>` (فیلد پلن)، `layer:<geom>` (خودکار از روی پارامترها). اپ‌های دیگر بررسی‌کننده‌ی خود را ثبت می‌کنند (مثلاً `satellite.credits`).

### ۵.۵ پنل مدیریت

مدل تازه‌ی `tools.ToolSetting` (یک ردیف برای هر کلید؛ نبودِ ردیف = پیش‌فرض پلاگین):

| فیلد | کاربرد |
|---|---|
| `key` | کلید پلاگین |
| `state` | فعال / بتا / خاموش |
| `beta_users` | کاربرانی که بتا را می‌بینند (کارکنان همیشه) |
| `plans` | پلن‌های مجاز (خالی = همه) |
| `order`، `featured` | ترتیب در گالری و «پیشنهادی» در خانه |
| `title_override`، `description_override` | متن بازاریابی بدون deploy |
| `timeout_s`، `daily_limit` | سقف زمان اجرا و تعداد اجرای روزانه‌ی هر کاربر |
| `note` | یادداشت داخلی (مثلاً «خاموش به‌خاطر خطای ...») |

صفحه‌ی «افزونه‌ها و ابزارها» (گروه تازه‌ی «محصول و ابزارها» در `core/admin_nav.py`)، طبق سیستم طراحی پنل:
- فهرست با چیپ فیلتر (فعال، بتا، خاموش، خطای بارگذاری)، ستون‌ها: آیکون و عنوان، کلید، نسخه، منبع (داخلی/اپ/بسته)، اجرای ۳۰ روز، درصد شکست، میانگین زمان؛ عملیات ردیف در منوی ⋯ (فعال/بتا/خاموش، آزمون سلامت، مشاهده‌ی اجراها).
- فرم با `TabbedAdminMixin`: «انتشار» (وضعیت، پلن، بتا)، «نمایش» (متن‌ها، ترتیب)، «محدودیت»، «فنی» (فقط‌خواندنی: پارامترها، پیش‌نیازها، ستون‌های خروجی، مسیر ماژول، خطای بارگذاری).
- `ToolRun` در ادمین: فیلتر ابزار/وضعیت/تاریخ، لینک به Job.
- شمارنده‌ی `badges()`: تعداد پلاگین با خطای بارگذاری یا شکست بالای ۲۰٪ در ۲۴ ساعت.
- آمار داشبورد ادمین (`core/admin_dashboard.py`): پراستفاده‌ترین ابزارها.
- **آزمون سلامت:** دکمه‌ای که `sample` پلاگین (داده‌ی نمونه‌ی کوچک) را روی پایگاه آزمون سرور اجرا می‌کند و نتیجه را ثبت می‌کند.

تنظیمات در کش نگه داشته می‌شود (با `post_save` باطل می‌شود) تا گالری کوئری اضافه نزند.

### ۵.۶ چرخه‌ی توسعه‌ی تیم
1. `python manage.py startplugin isodistance --category network` ← پوشه با `plugin.py`، `tests.py` (آزمون ساخت SQL + آزمون PostGIS)، `kb.md`، و یادآوری افزودن آیکون.
2. توسعه و آزمون: `DJANGO_TESTING=1 python manage.py test tools.plugins.isodistance`.
3. `python manage.py tools_check` + `kb_check` + `ruff check .` در CI.
4. PR و بازبینی؛ ادغام با وضعیت پیش‌فرض **بتا**.
5. پس از deploy، ادمین در پنل آن را برای کارکنان آزمون می‌کند، بعد برای پلن‌ها **فعال** می‌کند.
6. خاموش کردن اضطراری از پنل، بدون deploy.

سند `docs/tool-plugins.md` (راهنمای نوشتن پلاگین، فهرست API، الگوهای امن SQL، چک‌لیست رابط) بخشی از کار است.

### ۵.۷ تعمیم به «هر بخش یک پلاگین» (فاز ۲)
همان الگو با یک رجیستری عمومی «نقطه‌ی توسعه» در `core/plugins.py`؛ هر اپ در `geopaygah_plugin.py` سهم خود را اعلام می‌کند:

| نقطه‌ی توسعه | امروز (ثابت) | بعد |
|---|---|---|
| ابزار تحلیل | `analysis/tools.py` | `tools.sdk` |
| نوع کار پس‌زمینه | `Job.Kind` + دیکشنری در `jobs/services.run` | `jobs.register(kind, handler, label, destination)`؛ `choices` قابل‌فراخوانی (جنگو ۵٫۲) |
| مقصد اعلان | `DESTINATIONS` در `notifications/services.py` | از ثبت نوع کار |
| بخش ریل پایگاه و Ctrl+K | `GROUPS` در `core/templatetags/ws.py` | `ws.register_section(...)` |
| گروه ناوبری ادمین و شمارنده | `GROUPS`، `badges()` در `core/admin_nav.py` | `admin_nav.register_group/badge` |
| کارت خانه و آمار داشبورد | `_home`، `admin_dashboard.py` | ثبت کارت |
| راهنما | `kb/content` | پوشه‌ی `kb/` هر پلاگین |
| ابزار برای دستیار/پرسش فارسی و REST | ندارد | رجیستری برای هر ابزار JSON Schema می‌دهد ← فراخوانی تابع مدل زبانی و `/api/tools/` |

در پنل ادمین یک صفحه‌ی «افزونه‌ها» همه‌ی پلاگین‌ها و سهمشان (ابزار، نوع کار، بخش ریل…) را با وضعیت نشان می‌دهد؛ کلید «خاموش» یک پلاگین همه‌ی سهم‌هایش را پنهان می‌کند.
نکته: مدل‌ها و مهاجرت‌های پایگاه داده همچنان در اپ جنگو می‌مانند؛ پلاگینی که مدل دارد باید اپ نصب‌شده باشد (`INSTALLED_APPS`)، پس «روشن/خاموش» آن در ادمین یعنی پنهان کردن رابط و رد کردن اجرا، نه حذف جدول.

## ۷. پیامدها

**آسان‌تر می‌شود:** افزودن ابزار (یک پوشه به‌جای ۷+ فایل)؛ کار موازی تیم بدون تعارض؛ خاموش کردن اضطراری؛ انتشار تدریجی (بتا)؛ فروش ابزار بر اساس پلن؛ آزمون مستقل هر ابزار؛ ابزار از اپ‌های دیگر (ماهواره، رستر، نقشه‌برداری).

**سخت‌تر می‌شود:** API پلاگین باید پایدار و نسخه‌دار بماند (`api_version`)؛ یک لایه‌ی انتزاع بیشتر برای اشکال‌زدایی؛ نگهداری کش تنظیمات.

**ریسک‌ها و راه کنترل**
- *تغییر ناخواسته‌ی SQL هنگام بازسازی* ← آزمون SQL طلایی پیش از شروع.
- *پلاگین معیوب سایت را بخواباند* ← بارگذاری جداشده با ثبت خطا + system check در CI.
- *کد ناامن در پلاگین* ← قرارداد `Composable`، بدون اتصال خام، بازبینی PR، اجرای نقش مشتری، `statement_timeout` و سقف ردیف (`guard`).
- *تنظیم ادمین با کد ناهماهنگ شود (کلید حذف‌شده)* ← ردیف‌های یتیم در ادمین با نشان «پلاگین نصب نیست».

**باید بعداً بازبینی شود:** نیاز واقعی به فاز ۳؛ جدا کردن اتصال نقش مشتری از `SET ROLE`؛ صف جدا یا اولویت برای ابزارهای سنگین.
