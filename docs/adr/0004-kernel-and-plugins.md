# ADR-0004: بازطراحی ژئوپایگاه به «هسته + پلاگین»

**وضعیت:** پیشنهادی (منتظر تأیید؛ هیچ کدی تغییر نکرده)
**تاریخ:** ۱۴۰۵/۰۸/۲۰ (2026-11-11)
**تصمیم‌گیرنده:** مالک محصول + تیم توسعه
**مرتبط:** [0001 SDK ابزار](0001-tool-plugins.md) · [0002 سکوی پلاگین و بارگذاری](0002-plugin-platform.md) · [0003 نقشه‌ی قابلیت‌ها](0003-capability-map.md)
**این سند چه چیزی را عوض می‌کند:** ۰۰۰۲ پلاگین را «کنار» سامانه‌ی فعلی می‌گذاشت؛ این سند خودِ سامانه را به هسته و پلاگین تبدیل می‌کند، و سه چیز به ۰۰۰۲ اضافه می‌کند: مجوز برای مشتری خاص، صفحه‌ساز یکدست، و صف پردازش سنگین و داده‌ی زنده.

## ۲. وضعیت فعلی به عدد (اندازه‌گیری از کد)

| سنجه | مقدار |
|---|---|
| کد پایتون (بدون آزمون و مهاجرت) | حدود ۳۴ هزار خط در ۲۰ اپ |
| آزمون | حدود ۱۶ هزار خط (**سرمایه‌ی اصلی برای بازطراحی امن**) |
| قالب / JS / CSS | ۷٫۲ / ۹٫۵ / ۳٫۹ هزار خط |
| بزرگ‌ترین اپ | `databases`: ۸٫۱ هزار خط (ساخت پایگاه، مرورگر، ویرایش، یافتن، ورود، SQL، تیم، مصرف) |
| اپ‌هایی که `core` به آن‌ها وابسته است | ۹ اپ (حساب، صورتحساب، پایگاه‌ها، کارها، راهنما، نقشه، انتشار، ماهواره، دستیار) |
| اپ‌هایی که `databases` به آن‌ها وابسته است | ۱۲ اپ |
| حلقه‌ی وابستگی | `core ↔ databases ↔ jobs ↔ analysis/satellite/…`؛ `jobs` هشت اپ را می‌شناسد |
| فایل‌هایی که مستقیم به پایگاه مشتری وصل می‌شوند | ۲۸ فایل در ۱۰ اپ |
| سازوکار رویداد (signal) | ۱ مورد در کل پروژه |
| `SiteSettings` | یک مدل با ۱۳۸ فیلد (پیامک، درگاه، دستیار، ماهواره، فضای ابری، …) |
| کلید خارجی بین اپ‌ها | تقریباً همه به `databases.UserDatabase` و `jobs.Job` (یک «محور» طبیعی) |
| کارگر پس‌زمینه | یک حلقه، **یک کار در هر لحظه**، صف FIFO واحد |
| «مشتری» | امروز = یک کاربر مالک + اعضای هر پایگاه؛ موجودیت «سازمان» نداریم (فقط یک فیلد متنی) |

**جمع‌بندی:** امروز جهت وابستگی **برعکسِ** هدف است: `core` و `databases` همه را می‌شناسند. خبر خوب: داده‌ها یک محور روشن دارند (`UserDatabase`) و آزمون‌ها پوشش خوبی می‌دهند؛ پس بازطراحی تدریجی شدنی است و بازنویسی از صفر لازم نیست.

## ۳. معماری هدف

```
┌──────────────────────────── پلاگین‌ها ────────────────────────────┐
│ سیستمی (همراه ایمیج)   │ قابلیت (عمومی/پلنی)   │ اختصاصی مشتری │
│ حساب، صورتحساب، میزبانی │ جدول‌ها، ابزارها، نقشه، │ ردیابی زنده،   │
│ PostGIS، پشتیبانی، راهنما│ انتشار، برداشت، ماهواره │ پایش، …        │
└───────────────┬───────────────────────────────────────────────────┘
                │ فقط از راه SDK (قراردادهای پایدار و نسخه‌دار)
┌───────────────▼──────────────── SDK ──────────────────────────────┐
│ نقاط توسعه · رویدادها · دروازه‌ی داده‌ی مشتری · کیت صفحه · کارها  │
│ مجوزها · تنظیمات · اعلان · ذخیره‌گاه · آزمون‌یار                  │
└───────────────┬───────────────────────────────────────────────────┘
┌───────────────▼──────────────── هسته ─────────────────────────────┐
│ چرخه‌ی عمر پلاگین · هویت و فضای کار · موتور مجوز · صف و زمان‌بند  │
│ گذرگاه رویداد · دروازه‌ی اتصال · قاب رابط و سیستم طراحی          │
│ ثبت تنظیمات · رویدادنگاری · قاب پنل مدیریت                        │
└────────────────────────────────────────────────────────────────────┘
        هسته فقط به جنگو و کتابخانه‌ها وابسته است، نه به هیچ پلاگینی
```

### قاعده‌ی وابستگی (با ابزار در CI اجبار می‌شود، نه با قول)
1. هسته هیچ پلاگینی را import نمی‌کند.
2. پلاگین فقط SDK را import می‌کند، نه درون هسته را.
3. پلاگین به پلاگین دیگر فقط وقتی وابسته است که در مانیفست `requires` اعلام کرده باشد، و فقط از **API عمومی** آن (`<plugin>/api.py`) استفاده می‌کند.
4. ارتباط بدون وابستگی از راه **رویداد** است (مثلاً «کار تمام شد»، «پایگاه ساخته شد»).

اجبار با `import-linter` در CI به‌صورت «چرخ‌دنده»: فهرست تخلف‌های فعلی ثبت می‌شود و فقط اجازه‌ی کم شدن دارد.

### هسته دقیقاً چه دارد (و چرا)

| ماژول هسته | مسئولیت | امروز کجاست |
|---|---|---|
| `kernel.plugins` | مانیفست، رجیستری نقاط توسعه، چرخه‌ی عمر، بارگذاری ایمن، نسل | ندارد |
| `kernel.identity` | کاربر، نشست، مجوز ادمین | `accounts` (بخشی) |
| `kernel.workspace` | **فضای کار** (همان `UserDatabase` به‌عنوان محور)، مالک، اعضا و نقش، **سازمان/مشتری** | `databases.models` (بخشی) |
| `kernel.entitlements` | چه کسی به چه قابلیتی دسترسی دارد (بخش ۶) | پراکنده در `Plan` و if‌ها |
| `kernel.tenantdb` | **تنها** راه اتصال به پایگاه مشتری؛ نقش مشتری، مهلت، سقف، ثبت | `Explorer` + ۲۸ فایل |
| `kernel.jobs` | صف، کلاس منابع، زمان‌بند، پیشرفت؛ نوع کار را پلاگین ثبت می‌کند | `jobs` (با دیکشنری ثابت) |
| `kernel.events` | گذرگاه رویداد هم‌گام/ناهم‌گام با بودجه‌ی زمانی | ندارد |
| `kernel.ui` | قاب برنامه، ریل، Ctrl+K، سیستم طراحی، آیکون، **کیت صفحه** | `core`، `templates/base.html`، `ds.css` |
| `kernel.settings` | ثبت تنظیمات: هر پلاگین طرح تنظیمات خودش؛ راز رمزنگاری‌شده | `SiteSettings` (۱۳۸ فیلد) |
| `kernel.notify` | مرکز اعلان و کانال‌ها | `notifications` |
| `kernel.audit` | ردپای تغییرناپذیر | `ActivityLog` (بخشی) |
| `kernel.dash` | قاب پنل، ناوبری، داشبورد؛ محتوا از پلاگین‌ها | `core/admin_*` |

**تصمیم مهم — «فضای کار» در هسته می‌ماند.** همه‌ی کلیدهای خارجی به `UserDatabase` می‌رسند؛ اگر آن را هم پلاگین کنیم هسته چیزی برای اتصال پلاگین‌ها به هم ندارد و هر پلاگین باید به پلاگین دیگری وابسته شود. پس هسته «فضای کار و اعضایش» را می‌شناسد، ولی **ساخت و میزبانی PostGIS** (سرورها، provisioner، pgbouncer) یک پلاگین سیستمی است که پشت یک قرارداد می‌نشیند.

### سه دسته پلاگین

| دسته | نمونه | چگونه می‌آید | می‌شود خاموش کرد؟ |
|---|---|---|---|
| **سیستمی** | ورود و ثبت‌نام، صورتحساب و درگاه، میزبانی PostGIS، بکاپ، پشتیبانی، راهنما | داخل مخزن و ایمیج (استقرار عادی) | نه، یا فقط با جایگزین |
| **قابلیت** | جدول‌ها، ورود فایل، SQL، یافتن، ابزارها، پرسش فارسی، نقشه، انتشار، REST، برداشت، ماهواره، کلاس درس | ابتدا داخل مخزن؛ به‌تدریج قابل بارگذاری | بله |
| **اختصاصی** | ابزار سفارشی یک مشتری | بسته‌ی امضاشده، بارگذاری در ادمین | بله، برای همان مشتری |

**صادقانه درباره‌ی «همه‌چیز پلاگین»:** همه‌چیز از نظر *ساختار* پلاگین می‌شود (مانیفست، مرز، نقطه‌ی توسعه). ولی پلاگین‌های سیستمی (ورود، پرداخت، ساخت پایگاه) کدِ کاملاً مورد اعتمادند و با ایمیج می‌آیند؛ بارگذاری داغ آن‌ها از پنل سودی ندارد و فقط ریسک می‌آورد. آنچه «بارگذاری در ادمین» می‌شود قابلیت‌ها و ابزارهای اختصاصی است — یعنی همان جایی که سرعت توسعه و درآمد است.

## ۴. نگاشت اپ‌های فعلی به معماری هدف

| اپ فعلی | مقصد |
|---|---|
| `core` | → هسته (`ui`، `admin`، `settings`) + پلاگین «سایت عمومی» (صفحه‌ی اصلی، تماس، درباره) + راهنمای صفحه به پلاگین‌ها |
| `accounts` | هسته‌ی هویت + پلاگین سیستمی «روش‌های ورود» (پیامک، ایمیل) |
| `databases` | **شکسته می‌شود:** هسته (`workspace`، `tenantdb`) + پلاگین سیستمی «میزبانی PostGIS» + پلاگین‌های قابلیت: جدول‌ها، ویرایش، سازنده، ورود/خروج، SQL، یافتن، سلامت داده، مصرف، تیم |
| `jobs` | هسته‌ی صف + پلاگین سیستمی «بکاپ و بازگردانی» |
| `notifications` | هسته |
| `billing` | پلاگین سیستمی + نقطه‌ی توسعه‌ی «محصول افزودنی» و «درگاه» |
| `tools` + `analysis` | پلاگین «ابزارها» (میزبان ابزارهای پلاگینی) + پلاگین «پرسش فارسی» |
| `maps`، `publish`، `restapi` | سه پلاگین قابلیت؛ `publish` API عمومی برای کاشی می‌دهد که `maps` و `survey` مصرف می‌کنند |
| `survey`، `satellite`، `enterprise`، `iranmap`، `classroom` | هر کدام یک پلاگین قابلیت |
| `kb`، `assistant`، `support`، `analytics` | پلاگین سیستمی؛ محتوا را از پلاگین‌های دیگر می‌گیرند |
| `satgate` | سرویس جدا می‌ماند (همین حالا مستقل است) |

**نکته‌ی کلیدی کم‌ریسک:** برچسب اپ و نام جدول‌ها **عوض نمی‌شود**. پلاگین‌شدن یعنی تغییر مرز کد و جهت import، نه مهاجرت داده. داده‌ی مشتری و پایگاه پنل دست نمی‌خورد.

## ۶. موتور مجوز: عمومی، پلنی، مشتری خاص، فروشی

### موجودیت تازه: «سازمان/مشتری»
امروز مشتری = یک کاربر. برای «ابزار خاص یک مجموعه» باید بشود قابلیت را به یک **سازمان** داد که چند کاربر و چند پایگاه دارد. پیشنهاد: مدل `Organization` در هسته؛ هر کاربر فعلی خودکار یک سازمان تک‌نفره می‌شود (بدون تغییر تجربه‌ی فعلی).

### مدل
| مفهوم | توضیح |
|---|---|
| **دیده‌شدن پلاگین** | `public` (همه می‌بینند) · `plan` · `private` (فقط مشتریانِ دارای مجوز؛ برای دیگران اصلاً وجود ندارد — نه در منو، نه در جست‌وجو، نه در راهنما) |
| **مجوز** (`Entitlement`) | پلاگین (یا قابلیتی از آن) × دارنده (همه / پلن / سازمان / فضای کار / کاربر) × منبع (پلن، خرید، اعطای دستی، آزمایشی) × انقضا × سقف‌ها (تعداد اجرا، حجم، دستگاه) |
| **محصول افزودنی** | پلاگین در صورتحساب یک محصول می‌شود: قیمت یک‌باره/دوره‌ای/مصرفی؛ پرداخت ← مجوز خودکار؛ برای قرارداد خاص، اعطای دستی با یادداشت و شماره‌ی قرارداد |
| **سنجش مصرف** | هر پلاگین می‌تواند واحد مصرف ثبت کند (مثل اعتبار ماهواره‌ی امروز)، برای صورتحساب مصرفی و سقف |

### رفتار
- بررسی مجوز در یک نقطه (`kernel.entitlements.allowed(subject, feature)`)، با کش و ابطال فوری؛ منو، صفحه، API، کار پس‌زمینه و راهنما همه از همان می‌پرسند. بدون مجوز: پاسخ ۴۰۴، نه «دسترسی ندارید» (تا وجود پلاگین خصوصی فاش نشود).
- پایان مجوز: داده‌ی مشتری می‌ماند، رابط فقط‌خواندنی یا پنهان می‌شود (قابل تنظیم برای هر پلاگین).
- داده‌ی پلاگین خصوصی در پایگاه خود همان مشتری است؛ نشت بین مشتریان به‌طور ساختاری ناممکن.

## ۷. رابط یکدست: کیت صفحه و «استودیوی پلاگین»

### اصل
**پلاگین HTML و CSS نمی‌نویسد.** صفحه را به‌صورت «طرح» (schema) توصیف می‌کند و هسته آن را با اجزای سیستم طراحی رندر می‌کند. نتیجه: یکدستی، راست‌به‌چپ، ۴۰۰ پیکسل، دسترس‌پذیری، حالت خالی و خطا **به‌طور ساختاری** تضمین است، نه با بازبینی.

### طرح صفحه
| لایه | اجزا |
|---|---|
| قاب | سربرگ (مسیر، عنوان، توضیح، دکمه‌ی اصلی، منوی ⋯)، زبانه‌ها، چیدمان (تک‌ستون، دوستون، نقشه + پنل، شبکه‌ی کارت) |
| بلوک | نقشه (لایه‌ها، لایه‌ی زنده، رستر/ماهواره)، جدول/فهرست با فیلتر، نمودار (۱۰ نوع فعلی)، کارت عددی، فرم، جزئیات، خط زمان، مراحل، رسانه، حالت خالی |
| فیلد فرم | متن، عدد (بازه)، چیپ/کاشی، کلید روشن‌خاموش، لایه، ستون، نقطه/محدوده روی نقشه، تاریخ شمسی، فایل، رنگ از توکن |
| داده | منبع: کوئری فقط‌خواندنی با نقش مشتری · نقطه‌ی کد ایزوله · مجموعه‌ی ذخیره‌گاه · جریان زنده |
| کنش | اجرای کار، بازکردن مودال، ذخیره، پیمایش، دانلود، تأیید |
| شرط و متن | نمایش شرطی بر اساس نقش/مجوز/داده؛ همه‌ی متن‌ها کلیددار و **قابل بازنویسی در ادمین** |

### سه راه ساخت صفحه (از ساده به قدرتمند)
1. **طرح دستی** (فایل در بسته) — برای توسعه‌دهنده؛ در گیت، قابل بازبینی.
2. **استودیوی پلاگین در پنل مدیریت** («پلاگین‌ساز»): چیدن بلوک‌ها، تعریف فیلد و منبع داده، ویرایش متن، پیش‌نمایش زنده‌ی دسکتاپ و ۴۰۰ پیکسل، سپس «ساخت بسته». خروجی استودیو **همان بسته** است و از **همان خط لوله‌ی بررسی، آزمون و تأیید** می‌گذرد (استودیو راه میان‌بر نیست؛ ابزار نوشتن است) و قابل خروجی به گیت.
3. **بلوک سفارشی** برای تعامل ویژه (مثلاً پخش مسیر ردیابی): یک جزء وب که فقط توکن‌های طراحی و API مرورگر سکو را دارد، داخل قاب صفحه می‌نشیند و جدا بازبینی می‌شود. قاعده: اگر بلوکی دو بار لازم شد، به کیت صفحه اضافه می‌شود.

**ترتیب پیشنهادی:** اول طرح و رندرکننده (پایه)، بعد استودیو روی آن. استودیو فقط «ویرایشگر طرح» است؛ ساختن آن پیش از پایدار شدن طرح دوباره‌کاری می‌آورد.

## ۸. نمونه‌ی شما: «GPS آنلاین + نقشه‌ی ماهواره + رصد زنده + پردازش سنگین» برای یک مشتری

| نیاز | قطعه‌ی سکو |
|---|---|
| ثبت موقعیت دستگاه‌ها | `ingest.endpoint` با توکن هر دستگاه و سقف نرخ؛ نوشتن در جدول زمان‌دار در شِمای پلاگین در پایگاه همان مشتری |
| نقشه با تصویر ماهواره | بلوک نقشه + لایه‌ی رستر (از پلاگین ماهواره/رستر، از راه API عمومی‌اش) |
| رصد زنده | `stream` + نوع لایه‌ی زنده |
| پردازش سنگین | کار با کلاس منابع «سنگین» در سرویس ایزوله |
| فقط برای یک مشتری | پلاگین `private` + مجوز به سازمان آن مشتری + محصول/قرارداد |
| هشدار | `notify` |

دو محدودیت زیرساختی فعلی که این نمونه آشکار می‌کند و **باید در طرح حل شود**:
1. **کارگر تک‌کاره:** امروز یک کار در هر لحظه اجرا می‌شود؛ پردازش سنگین یک مشتری بکاپ و ورود فایل بقیه را معطل می‌کند. ← صف چندکلاسه (`سبک`، `سنگین`، `سیستمی`) با سقف هم‌زمانی جدا و سهم هر مشتری؛ امکان کارگر اختصاصی (حتی سرور جدا) برای یک پلاگین پرمصرف.
2. **اتصال زنده:** وب با ۳ پردازه × ۴ نخ برای اتصال‌های طولانی (SSE/WebSocket) مناسب نیست؛ چند ده بیننده‌ی زنده سایت را کند می‌کند. ← شروع با نظرسنجی دوره‌ای (ساده، کافی برای به‌روزرسانی چندثانیه‌ای)؛ با اولین پلاگین واقعاً زنده، یک سرویس جدای `realtime` (ASGI) اضافه شود. دریافت پرحجم دستگاه‌ها هم در همان سرویس، نه در وب اصلی.

هیچ‌کدام از این‌ها به کد هسته‌ی اختصاصیِ آن مشتری نیاز ندارد؛ هسته یک‌بار توانمند می‌شود و بعد هر پلاگین زنده از آن استفاده می‌کند.

## ۹. امنیت (با فرض «فقط تیم خودمان»)

این فرض مدل را **ساده‌تر و سخت‌گیرتر** می‌کند:

| قاعده | توضیح |
|---|---|
| امضای اجباری برای همه‌ی سطح‌ها | بسته‌ی بدون امضای معتبر حتی وارد مرحله‌ی بررسی نمی‌شود. (در ۰۰۰۲ سطح ۱ بدون امضا مجاز بود؛ اینجا نه.) |
| امضا فقط در CI مخزن پلاگین‌ها | توسعه‌دهنده امضا نمی‌کند؛ ادغام در شاخه‌ی اصلی پس از بازبینی ← CI می‌سازد و امضا می‌کند. کلید خصوصی فقط در CI/سخت‌افزار؛ کلید عمومی فقط در تنظیم استقرار سرور (نه پایگاه داده) |
| بارگذاری ≠ تأیید | دو مجوز جدا؛ برای سطح ۳ دو نفر جدا (یا تأخیر زمانی + اعلان اگر تیم کوچک است) |
| ورود دومرحله‌ای ادمین | انجام شد (`accounts/admin_2fa.py`): پس از رمز، TOTP یا کد بازیابی؛ کارهای حساس تأیید تازه می‌خواهند |
| کمترین دسترسی | پلاگین فقط قابلیت‌های اعلام‌شده در مانیفست را دارد؛ اتصال به پایگاه مشتری همیشه با نقش خود مشتری و فقط از `kernel.tenantdb` |
| جداسازی | سطح ۲ در سرویس بدون راز و بدون شبکه؛ سطح ۳ فقط پس از پیش‌پرواز |
| راز پلاگین | تنظیمات محرمانه رمزنگاری‌شده، فقط برای همان پلاگین قابل خواندن |
| وابستگی | نصب از اینترنت ممنوع؛ فقط فهرست مجاز یا همراه بسته با هش. (قفل نسخه‌ی `smart-spatial-system` در `entrypoint.sh` هم باید انجام شود) |
| ردپا و توقف اضطراری | ثبت همه‌ی کنش‌ها؛ خاموشی فوری هر پلاگین؛ حالت امن کل سکو |

خط لوله‌ی بارگذاری تا فعال‌سازی همان ۹ مرحله‌ی ۰۰۰۲ است.

---

**اصلاح پس از پیاده‌سازی مرحله‌ی «ج» (یافته از کد):** اتصال به داده‌ی مشتری از ابتدا با حساب ادمین سرور نبوده است؛ برای هر پایگاه یک نقش محدود `<user>_web` (عضو نقش مشتری، فقط به پایگاه همان مشتری) استفاده می‌شود و نوشتن با `SET ROLE` به نقش مالک همان مشتری است. پس نگرانی «`SET ROLE` روی اتصال ادمین» در ۰۰۰۱ و ۰۰۰۲ وارد نبود؛ `RESET ROLE` هم فقط به همین نقش محدود برمی‌گردد. اتصال حالا در `kernel.tenantdb` متمرکز است.

**وضعیت مرحله‌ی «ج» (گام ۱ تا ۳):** قراردادهای `kernel.tenantdb` (اتصال)، `kernel.workspace` (دسترسی، میزبان، ساخت، اعلان)، `kernel.dataio` (GDAL) و `kernel.crypto` پیاده شد و بخش‌های دیگر دیگر ماژول‌های `databases` را جز `models` نمی‌شناسند. «بخش‌های پروفایل» (`kernel.profile`) هم نقطه‌ی توسعه شد و زبانه‌ی مدل زبانی را تحلیل می‌آورد. 

**وضعیت مرحله‌ی «د» (آغاز):** جهت وابستگی کامل شد: هیچ پلاگین سیستمی (حساب، هسته‌ی سایت، پایگاه داده، کارها، صورتحساب، پشتیبانی، اعلان، راهنما، دستیار، آمار) مستقیم یا غیرمستقیم پلاگین قابلیتی را import نمی‌کند (قرارداد سخت). ابزارهای این وارونگی: `kernel.events` (حذف پایگاه، حذف و تغییر نام جدول، کارت مصرف)، `kernel.home`، `kernel.profile`، `kernel.llm`، شیت‌های گزارش اکسل در `kernel.dash`. باقی‌مانده: شکستن `databases` به بخش‌های جدا (جدول‌ها، SQL، یافتن، ورود، سلامت داده…) که وابسته به سازوکار «نصب مسیر URL توسط پلاگین» است (مرحله‌ی «ز») و ارزش آن برای سکو کم‌تر از مجوز و بارگذاری است.

**وضعیت مرحله‌ی «ه» (مجوز و سازمان) — پیاده شد:**
- مدل‌ها در هسته (بدون کلید خارجی به پلاگین‌ها): `Organization`، `OrgMember`، `PluginState` (روشن/خاموش، باز/محدود)، `Entitlement` (دارنده: همه، پلن، سازمان، کاربر، فضای کار؛ انقضا؛ سقف‌ها؛ منبع).
- `kernel.entitlements.allowed(plugin, user=, ws=)`: پلاگین سیستمی همیشه مجاز؛ نبودن ردیف = باز؛ خاموش = برای همه ناپدید؛ محدود = مجوز معتبر. مالک و اعضای سازمانِ مالک فضای کار هم دیده می‌شوند. حافظه‌ی پردازه با TTL ۲۰ ثانیه و ابطال فوری با سیگنال.
- `kernel.gate.PluginGateMiddleware`: بر اساس ماژول نما، پلاگین خاموش/بدون مجوز ← ۴۰۴ (وجود پلاگین فاش نمی‌شود). مسیر محدودِ بدون کاربر پیش‌فرض بسته است؛ استثنا فقط با `@gate.public`.
- منوی ریل، کارت‌های خانه، Ctrl+K و زبانه‌های پروفایل با همین موتور فیلتر می‌شوند.
- پنل مدیریت: «پلاگین‌ها و مجوزها» (همگام‌سازی خودکار ردیف‌ها، کنش‌های گروهی، مجوز درون‌خطی با اعتبارسنجی دارنده، ثبت اعطاکننده) و «سازمان‌های مشتری».
- هنوز نیست: اتصال به صورتحساب (محصول افزودنی ← مجوز خودکار) و سنجش مصرف.

**وضعیت مراحل «ز» و «و» (سطح ۱: اعلانی) — پیاده شد:**
- کیت صفحه (`kernel.pagekit`): مشخصات (متن، کارت عددی، جدول، میله، نقشه)، SQL فقط‌خواندنی با نقش محدود، تراکنش فقط‌خواندنی، حد زمانی، سقف ردیف، یک دستور، پارامتر bind؛ منو و آدرس `dashboard/<pk>/p/<پلاگین>/<صفحه>/`؛ رفتار واقعی PostgreSQL در آزمون (با `TEST_PG_HOST`).
- بسته‌ی پلاگین (`kernel.pkg`): zip امن، امضای Ed25519 با کلید ناشر در تنظیم استقرار، خط لوله‌ی بررسی با گزارش ماندگار، اصل دونفره، فعال‌سازی با وضعیت «محدود و بدون مجوز»، بازگشت و غیرفعال‌سازی، بارگذاری پویا در رجیستری هر پردازه (ظرف ۲۰ ثانیه)، ابزار `plugin_keygen`/`plugin_pack`/`plugin_check`.
- سطح ۲: بسته‌ی دارای `code/` با handler در بلوک کیت صفحه، جعبه‌ی زیرپردازه و سرویس plugin-runner (docs/plugins/tier2.md). هنوز نیست: سطح ۳، اجرای پس‌زمینه‌ی سطح ۲، فرم و نوشتن در صفحه‌ها، سرویس `plugin-runner`، استودیوی پلاگین، سنجش مصرف و اتصال به صورتحساب.

## ۱۱. مسیر مهاجرت: تدریجی، نه بازنویسی

**اصل‌ها:** هیچ‌وقت «توقف و بازنویسی» نیست؛ هر مرحله قابل استقرار و برگشت‌پذیر است؛ رفتار کاربر تا مرحله‌ی «ه» عوض نمی‌شود؛ ۱۶ هزار خط آزمون فعلی در هر مرحله باید سبز بماند؛ نام جدول‌ها ثابت می‌ماند.

| مرحله | کار | نتیجه | برآورد* |
|---|---|---|---|
| **الف — درزهای هسته** | ساخت `kernel` کنار کد فعلی: رجیستری پلاگین و نقاط توسعه، گذرگاه رویداد، ثبت نوع کار، ثبت ناوبری (ریل، ادمین)، ثبت تنظیمات؛ اپ‌های فعلی به‌جای فهرست‌های ثابت از این‌ها ثبت‌نام می‌کنند؛ افزودن `import-linter` با فهرست تخلف فعلی | نقاط توسعه واقعی می‌شوند؛ بدون تغییر رفتار | ۳–۴ هفته |
| **ب — وارونه‌کردن وابستگی‌ها** | `core` و `jobs` و `notifications` دیگر هیچ اپی را import نکنند (راهنما، داشبورد ادمین، مقصد اعلان، handler کارها از رجیستری)؛ شکستن `SiteSettings` به طرح تنظیمات هر بخش (با حفظ داده) | هسته به هیچ‌چیز وابسته نیست | ۳–۴ هفته |
| **ج — دروازه‌ی داده و شکستن `databases`** | `kernel.tenantdb` تنها راه اتصال (۲۸ فایل)؛ جدا کردن `workspace` و «میزبانی PostGIS» از قابلیت‌ها (جدول‌ها، ویرایش، یافتن، ورود، SQL، سلامت، مصرف، تیم) | بزرگ‌ترین گره باز می‌شود | ۴–۶ هفته |
| **د — پلاگین‌شدن اپ‌ها** | مانیفست و API عمومی برای هر اپ؛ ابزارها طبق ۰۰۰۱؛ صفر شدن تخلف‌های `import-linter` | همه‌چیز ساختاراً پلاگین است | ۳–۵ هفته |
| **ه — مجوز و سازمان** | `Organization`، موتور مجوز، محصول افزودنی در صورتحساب، بخش‌های ادمین مربوط | فروش و فعال‌سازی برای مشتری خاص | ۳–۴ هفته |
| **و — بارگذاری در ادمین** | قالب بسته، امضا، خط لوله، سطح ۱، سپس سرویس ایزوله و سطح ۲ (۰۰۰۲)؛ صف چندکلاسه | توسعه با بارگذاری پلاگین | ۵–۷ هفته |
| **ز — کیت صفحه** | طرح صفحه، رندرکننده، بلوک‌ها، ذخیره‌گاه، زمان‌بند | منو و صفحه‌ی تازه بدون کد هسته | ۴–۶ هفته |
| **ح — نخستین پلاگین اختصاصی واقعی** | مثلاً ردیابی زنده؛ سرویس `realtime` در صورت نیاز | اثبات کل مسیر با یک مشتری | ۳–۵ هفته |
| **ط — استودیو و سطح ۳** | پلاگین‌ساز در ادمین؛ پیش‌پرواز و راه‌اندازی تدریجی برای اپ کامل | ابزار حرفه‌ای تیم | ۵–۸ هفته |

\* برآورد یک توسعه‌دهنده‌ی تمام‌وقت، **تخمینی و با عدم‌قطعیت زیاد**؛ جمع حدود ۸ تا ۱۲ ماه. با دو نفر، مرحله‌های «ه» و «و» و «ز» پس از «د» موازی می‌شوند. پس از مرحله‌ی «الف» برآوردها دقیق می‌شود.

**ترتیب را می‌شود برای درآمد زودتر عوض کرد:** اگر نخستین مشتریِ ابزار اختصاصی نزدیک است، مسیر کوتاه = الف ← ه ← و (فقط سطح ۱ و ۲) ← ز ← ح، و مرحله‌های ب، ج، د در پس‌زمینه ادامه پیدا کنند. هزینه‌اش: مدتی دو سبک کد کنار هم.

## ۱۳. پیامدها

**به دست می‌آید:** افزودن قابلیت بدون دست‌زدن به بقیه؛ ابزار اختصاصی قابل فروش؛ خاموش/روشن برای هر مشتری؛ تیم موازی؛ رابط یکدست تضمین‌شده؛ پایه‌ای برای هر حوزه‌ی علوم مکانی.

**هزینه و ریسک:**
- چند ماه بخشی از ظرفیت تیم صرف زیرساخت می‌شود، نه قابلیت تازه.
- SDK تعهد بلندمدت است؛ طراحی عجولانه‌ی قراردادها گران تمام می‌شود ← هر قرارداد اول با دو مصرف‌کننده‌ی واقعی محک بخورد.
- ریسک «انتزاع بیش از حد»: ساخت نقطه‌ی توسعه‌ای که هیچ پلاگینی لازمش ندارد ← نقطه‌ی توسعه فقط وقتی ساخته شود که یک قابلیت موجود یا سفارش واقعی آن را بخواهد.
- کیت صفحه هر رابطی را پوشش نمی‌دهد؛ استودیوی نقشه و برداشت میدانی رابط‌های سنگین اختصاصی دارند و مدتی به‌صورت «بلوک سفارشی بزرگ» می‌مانند.
- دو سرویس تازه (ایزوله و احتمالاً زنده) برای نگهداری.

**بازبینی:** پس از «الف» (دقت برآورد)، پس از «ح» (آیا سطح ۱ و ۲ برای سفارش‌های واقعی کافی است یا سطح ۳ زودتر لازم می‌شود).

## ۱۴. تصمیم‌هایی که لازم است
1. تأیید معماری هدف و قاعده‌ی وابستگی (بخش ۳)، از جمله ماندن «فضای کار» در هسته.
2. افزودن موجودیت «سازمان/مشتری» (بخش ۶).
3. ترتیب مهاجرت: مسیر کامل (الف تا ط) یا مسیر کوتاهِ درآمدمحور.
4. ظرفیت تیم: چند نفر و چه سهمی از زمان؟ (برآوردها به آن وابسته است.)
5. مخزن جدا برای پلاگین‌ها با CI امضاکننده.
6. ~~ورود دومرحله‌ای برای پنل مدیریت~~ — انجام شد: TOTP اجباری برای `/manage/` (رمز هر گام یک‌بار، کد بازیابی، قفل ۵ شکست/۱۵ دقیقه، سقف نشست ۱۲ ساعت) و تأیید تازه برای بارگذاری و فعال‌سازی پلاگین.
7. نخستین پلاگین اختصاصی واقعی برای محک (ردیابی زنده یا مورد دیگر).
